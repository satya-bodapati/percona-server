Short design · Percona Server 8.4 · proposal, not implemented

Visible GTID Stream

The server tells a proxy which GTIDs a query can already see, so reads that follow a write can go to a replica safely.

1. The problem we are solving

An application writes a row through ProxySQL and reads it back straight away. The write goes to the primary; the read may go to a replica. If the replica has not applied the write yet, the application does not see its own row.

ProxySQL avoids this with GTIDs:

  • The primary returns the GTID of each commit to ProxySQL in the OK packet.
  • ProxySQL keeps, per replica, the set of GTIDs that replica has. A read goes only to a replica whose set contains the client's last GTID.

To keep those sets current, a helper process (proxysql_binlog_reader) reads each replica's binlog and reports every GTID it sees.

2. What goes wrong today

A transaction is written to the replica's binlog before it is committed in InnoDB. The reader reports the GTID when it appears in the binlog. For a short time ProxySQL believes the replica has the write, sends the read there, and the row is not visible yet.

The two positions differ on purpose. The binlog must be written first because it decides, after a crash, which transactions are committed. Replication, and semisync in particular, must be able to send a transaction before it is committed. So the existing position cannot simply be moved later.

The gap is usually under a few milliseconds, but it grows without limit when the fsync or a semisync acknowledgement is slow.

3. Where the server knows what is committed

In the last stage of group commit. One thread, the group leader, does three things in order for the whole group:

  1. InnoDB commits each transaction. InnoDB removes the transaction from its list of active transactions. From that moment every new query sees its rows.
  2. The server adds the group's GTIDs to gtid_executed. This is the in-memory set behind @@global.gtid_executed.
  3. New: the leader records the binlog position where the group ends. We call it the last committed position. Everything in the binlog before it is committed.

Every transaction that has a GTID in the binlog passes through this stage: client transactions, replication applier threads (single or parallel), DDL, and the empty transactions a filtered replica writes. With binlog_order_commits=ON, groups commit in the order they were written, so one position is enough to describe what is committed.

InnoDB itself is not changed. It does not need to know about the position; the leader records it right after InnoDB has finished.

4. Sending it to many clients without slowing commits

The committing side does one small thing per group: store the new position and wake any waiting stream threads. It never builds a list, never copies GTIDs, and never waits for a client.

In practice there is usually one client per server: the reader process that feeds ProxySQL. More are allowed. No extra thread is created for a client. Every MySQL connection already has a server thread, and when the client starts the stream that thread does the sending, as it does for a replica today. It reads the binlog file, which already contains every GTID, up to the last committed position, and sends only the GTID events. When it reaches the position it sleeps until the leader moves it.

There is no queue between committers and clients, so there is nothing to fill up, nothing to trim, and no per-client state beyond a file offset.

5. Same mechanism as binlog_end_pos

Replication already works exactly this way. The leader stores binlog_end_pos under a small dedicated mutex and signals; each replica's dump thread reads the file up to it and waits there. We add a second position of the same kind and reuse the dump thread code.

6. How a client connects and reads

If the connection drops, or the server restarts or resets its GTIDs, the client connects again and starts from step 1. It needs no saved state, because step 4 always gives the full set.

7. How the client understands the stream

The stream uses ordinary binlog events, so any existing binlog library can decode it. The client sees three kinds that matter:

EventMeaningClient does
Previous GTIDseverything visible on this server right nowreplace its set with this one
GTIDthis transaction has just become visibleadd it to the set
Heartbeatserver is alive, nothing newnothing

The client keeps a set, not one "last GTID". A replica can have GTIDs from several sources, and a parallel applier can commit number 12 before number 11. So there is no single last value. The question ProxySQL asks is "is the client's GTID in this replica's set?", which is the check it already does today.

While a client is disconnected, or before it has received the first Previous GTIDs event, it treats the replica's set as unknown and does not send causal reads there.

Settings this needs

gtid_mode=ON, binlog on, log_replica_updates=ON on replicas, binlog_order_commits=ON. All are defaults in 8.4. If one is off, the server refuses the stream with an error naming it.
