Visible GTID Stream Plugin

A plugin that pushes each GTID to a client the moment a query on this server can see it. Installable on an unmodified server.

1. The problem

ProxySQL sends a read to a replica only if the replica already has the client's last write, identified by its GTID. It learns which GTIDs a replica has from a helper that reads the replica's binlog.

A transaction reaches the binlog before it is committed in InnoDB. So the helper reports the GTID too early, and for a short time a read sent to that replica does not see the row.

2. What we build

One plugin with three parts. The server is not changed.

3. Where the plugin learns that a GTID is committed

From the server's after_commit hook, the same interface semisync uses. The server calls it once per transaction, in this order:

  1. InnoDB commits the transaction. New queries now see its rows.
  2. The server adds the GTID to gtid_executed.
  3. The server calls after_commit and passes the transaction's GTID to the plugin.

This order holds for client sessions and for replication applier threads, single or parallel, and with binlog_order_commits ON or OFF.

4. From the hook to the client, without slowing commits

The hook is on the commit path, so it does almost nothing: it appends the GTID to a ring and wakes the stream loop.

  • The ring is bounded. Entries are numbered. When it is full, the oldest entry is overwritten. The hook never waits and never does I/O.
  • When no client is connected, the hook returns at once after one check.
  • The stream loop remembers the number of the last entry it sent. It sends what is newer and sleeps when it has caught up.
  • A slow client falls behind until its position is overwritten. The loop then sends the full set again and continues from the present. Commits are never delayed. A status counter records each such overrun.

5. How the client connects

The client starts a normal binlog dump, as any replica or binlog reader does, with one extra variable. The server calls the plugin at the start of every dump, on that connection's thread. For a connection that set the variable, the plugin keeps the thread and runs the stream loop on it. No binlog data is sent on that connection.

  • Real replicas are not affected. A connection without the variable is left alone and receives the binlog as always. Each connection has its own thread.
  • Security is the server's. Login, TLS and the replication privilege apply as for any replica. There is no new port.
  • Reconnect. If the connection drops or the server restarts, the client connects again. It needs no saved state because step 4 always sends the full set.

6. What the client receives

Ordinary binlog events, built by the plugin with the server's own event code. Any binlog client library can decode them.

EventMeaningClient does
Previous GTIDseverything visible on this server right nowreplace its set with this one
GTIDthis transaction has just become visibleadd it to the set
Heartbeatserver is alive, nothing newnothing

The client keeps a set and asks "is this GTID in the set?". There is no single "last GTID", because a replica has GTIDs from several sources and a parallel applier can commit them out of numeric order.

This is the same client contract as in the core design. A client written for the plugin works unchanged if the feature later moves into the server.

7. What the hook misses, and how the stream stays correct

In a few rare cases a GTID becomes part of gtid_executed without a call to the hook:

  • a transaction that changed a non-transactional table and then rolled back;
  • SET GLOBAL gtid_purged;
  • a GTID committed with sql_log_bin=0.

The stream covers them with step 7: every N seconds the loop sends the full set again, read from gtid_executed. A GTID the hook missed therefore appears after at most N seconds. The same step repairs the client's set after a ring overrun.

RESET BINARY LOGS AND GTIDS has its own hook. The plugin sends the full set immediately, and the client's set shrinks.

8. Limits

LimitDetail
Settingsgtid_mode=ON, binlog on, log_replica_updates=ON on replicas. The hook fires only for transactions written to the binlog. Otherwise the plugin refuses the stream with an error naming the setting.
Rare cases are lateThe three cases in section 7 are reported up to N seconds late. Never early.
Installing other replication pluginsWhile a stream is connected, INSTALL or UNINSTALL of a replication plugin (for example semisync) waits. The plugin has a switch that disconnects all streams, to let such a statement proceed. Other replicas keep running meanwhile.
Plugin, not componentThe commit hook is offered to plugins only. The plugin is built per server version, like semisync.
Cost of commit hooksOnce any plugin registers for commit hooks, the server calls them for every transaction. Semisync and Group Replication pay this today. To be measured.

9. To confirm with a prototype

  • The server accepts the dump request and reaches the plugin before sending anything, for both forms of the dump command.
  • A stream loop that stays inside the hook reacts to client disconnect, KILL, shutdown and plugin uninstall.
  • The GTID passed to the hook is always the transaction's own.
  • Overhead of the hook on a busy server, with and without a client.
